# Findings Register — Module 1: Cluster & Workload Security Review

## Scope and Evidence Base

This register is based on a hands-on review of the cloned kubernetes-goat repository under `reference-target/`, including Kubernetes manifests, Helm templates, Dockerfiles, shell scripts, and the AWS KinD-on-EC2 CDK setup. No real EKS cluster or production environment was available, so findings are evidenced from repository artefacts and interpreted against the programme context in `README.md`.

Severity ratings use `01-findings/severity-methodology.md`. Finding IDs are stable and must be reused by later modules.

## Executive View

| Severity | Count | Main themes |
|---|---:|---|
| Critical | 6 | Cluster-admin-equivalent RBAC, privileged containers, host filesystem/runtime socket access |
| High | 12 | Secrets in manifests/env vars, no NetworkPolicy, NodePort exposure, weak image provenance, missing admission controls/logging |
| Medium | 7 | Missing resource requests, outdated lab node/tooling, no seccomp/AppArmor on broad set of workloads, broad egress |
| Low | 1 | Hardcoded demo/internal URLs |

## Findings

| ID | Severity | Domain | Title | Exact location | Why this severity | Risk statement | Remediation and effort |
|---|---|---|---|---|---|---|---|
| **K8S-001** | **Critical** | RBAC | `superadmin` ServiceAccount is bound to `cluster-admin` | `reference-target/scenarios/insecure-rbac/setup.yaml:1-18`; resource `ServiceAccount/superadmin` in `kube-system`, `ClusterRoleBinding/superadmin` to `ClusterRole/cluster-admin` | Critical because it grants a non-system workload identity full cluster control. Not lower because this is the same failure mode as the trigger incident; not higher because severity tops out at Critical. | A pod or CI job using this service account can read every Secret, alter RBAC, deploy privileged workloads, and persist across namespaces. This directly mirrors the audit incident where a CI service account had `cluster-admin`. | Delete the binding; replace with a namespace-scoped Role containing only required verbs/resources; add CI service accounts to an allowlisted RBAC review process. **Effort: 4-8 hours** for manifest fix, **1-2 days** to add review gates. |
| **K8S-002** | **Critical** | RBAC | Helm `pwnchart` creates wildcard cluster-admin-equivalent ClusterRole | `reference-target/infrastructure/helm-tiller/pwnchart/templates/clusterrole.yaml:1-8`; resource `ClusterRole/all-your-base` with `apiGroups: ["*"], resources: ["*"], verbs: ["*"]` | Critical because wildcard on API groups, resources, and verbs is cluster-admin-equivalent. Not lower because it permits RBAC mutation and Secret access cluster-wide. | Any principal bound to this role can take over the cluster, including creating new persistent admin bindings after initial access. | Remove the chart from deployable paths; enforce policy blocking wildcard ClusterRoles except approved platform roles; require least-privilege Helm chart review. **Effort: 1 day**. |
| **K8S-003** | **Critical** | RBAC | Helm `pwnchart` binds wildcard ClusterRole to default ServiceAccount by default | `reference-target/infrastructure/helm-tiller/pwnchart/templates/clusterrolebinding.yaml:1-13`; defaults from `reference-target/infrastructure/helm-tiller/pwnchart/values.yaml:4-5` bind `default/default` | Critical because it turns the namespace default ServiceAccount into a cluster admin. Not lower because pods use the default service account automatically when no explicit identity is set. | A normal pod deployed into the default namespace could inherit full cluster control without the workload owner realising it. | Remove the ClusterRoleBinding template; prohibit ClusterRoleBinding subjects using `default` service accounts; require explicit service accounts per workload. **Effort: 1 day**. |
| **K8S-004** | **Critical** | Pod Security / Node Hardening | `system-monitor` runs privileged with host namespaces and read-write host root mount | `reference-target/scenarios/system-monitor/deployment.yaml:25-41`; resource `Deployment/system-monitor-deployment`; `hostPID: true`, `hostIPC: true`, `hostPath: /`, `mountPath: /host-system`, `allowPrivilegeEscalation: true`, `privileged: true` | Critical because it is a direct node compromise path. Not lower because the host root filesystem is mounted read-write and runtime detection is absent. | A compromised `system-monitor` container can modify host files, inspect host processes, and escape normal Kubernetes isolation. On EKS managed nodes, that can expose kubelet credentials and affect neighbouring workloads. | Remove host namespace use and host root mount; run as non-root with `allowPrivilegeEscalation: false`; isolate any required diagnostics into break-glass DaemonSets with approval. **Effort: 1-2 days**. |
| **K8S-005** | **Critical** | Pod Security / Node Hardening | `health-check` privileged container can access host container runtime sockets | `reference-target/scenarios/health-check/deployment.yaml:51-64` and hostPath volumes at `:81-98`; resource `Deployment/health-check-deployment` | Critical because privileged + Docker/containerd socket access is a container escape pattern. Not lower because it enables creating privileged containers on the node. | If the app is compromised, the attacker can talk to Docker/containerd on the host and start containers with host mounts, bypassing Kubernetes RBAC controls. | Remove runtime socket mounts; replace socket detection with Kubernetes API health checks; block privileged pods and socket hostPaths via admission policy. **Effort: 1-3 days**. |
| **K8S-006** | **Critical** | Pod Security / Node Hardening | `docker-bench-security` DaemonSet has hostNetwork, hostPID, hostIPC, privileged containers, and runtime socket mounts | `reference-target/scenarios/docker-bench-security/deployment.yaml:27-72` plus hostPath volumes at `:106-138`; resource `DaemonSet/docker-bench-security` | Critical because a DaemonSet runs on every node with privileged host access. Not lower because compromise has fleet-wide node blast radius. | A vulnerability in the scanner container becomes a node-level compromise on every scheduled node and bypasses NetworkPolicy through `hostNetwork`. | Run kube-bench as a short-lived controlled job in an isolated admin namespace; remove privileged mode except where explicitly required; prefer managed CIS scanning in EKS/AKS/GKE. **Effort: 2-3 days**. |
| **K8S-007** | **High** | RBAC / Secrets | Namespace Role `secret-reader` grants read access to all core resources, not just Secrets | `reference-target/scenarios/hunger-check/deployment.yaml:7-15`; resource `Role/secret-reader` in `big-monolith` with `resources: ["*"]`, verbs `get/list/watch` | High because it exposes all namespace Secrets and workload metadata. Not Critical because it is namespace-scoped and read-only. | A compromised `hunger-check` pod can enumerate and read all core API objects in `big-monolith`, including Secrets unrelated to its business function. | Change resources to the exact Secret names needed, or remove API read access entirely; apply RBAC unit tests with `kubectl auth can-i`. **Effort: 4-8 hours**. |
| **K8S-008** | **High** | RBAC / Secrets | `big-monolith-sa` is bound to the over-broad `secret-reader` Role | `reference-target/scenarios/hunger-check/deployment.yaml:17-35` and workload use at `:69`; resources `RoleBinding/secret-reader-binding`, `ServiceAccount/big-monolith-sa`, `Deployment/hunger-check-deployment` | High because the vulnerable workload identity receives the over-broad permission. Not Critical because blast radius is limited to one namespace. | The application container has API permissions that are wider than required, so app compromise becomes Secret and namespace reconnaissance. | Bind a narrow Role to only required resources, or use External Secrets Operator with no in-pod list/watch rights. **Effort: 4-8 hours**. |
| **K8S-009** | **High** | Secrets | Kubernetes Secrets are committed as base64 data in manifests | `reference-target/scenarios/hunger-check/deployment.yaml:37-53`; `Secret/vaultapikey`, `Secret/webhookapikey`; `reference-target/scenarios/system-monitor/deployment.yaml:1-8`; `Secret/goatvault` | High because secrets in Git are copied into clone history and CI logs. Not Critical here because values are synthetic kubernetes-goat demo secrets, not live credentials. | In production, this pattern would leak API keys to every repo reader and every CI system that checks out the repo. Base64 is encoding, not encryption. | Move to AWS Secrets Manager/Azure Key Vault/GCP Secret Manager via External Secrets Operator; rotate any real value ever committed. **Effort: 1-2 days** for pattern, **hours** per secret. |
| **K8S-010** | **High** | Secrets | Secret value is injected into `system-monitor` as an environment variable | `reference-target/scenarios/system-monitor/deployment.yaml:47-52`; env var `K8S_GOAT_VAULT_KEY` from `Secret/goatvault` | High because env vars leak via process inspection, crash dumps, and some debug tooling. Not Critical because it exposes one namespace Secret rather than cluster-wide data. | Anyone with pod exec/debug visibility can read the vault key from the process environment, and many observability stacks accidentally collect env vars. | Prefer projected Secret volume with file permissions, short TTL, and app reload support; longer-term use workload identity to fetch secrets at runtime. **Effort: 1 day**. |
| **K8S-011** | **High** | Secrets / Platform | No evidence of etcd encryption-at-rest configuration | No `EncryptionConfiguration`, kube-apiserver `--encryption-provider-config`, or managed EKS encryption config found under `reference-target/`; kube-bench mounts etcd paths at `reference-target/scenarios/kube-bench-security/master-job.yaml:76-77` | High because native K8s Secrets are used and no encryption control is evidenced. Not Critical because repository evidence cannot prove a real managed control plane lacks encryption. | If etcd snapshots or node/control-plane storage are exposed, Kubernetes Secrets may be recoverable without application compromise. | For EKS, enable KMS envelope encryption on cluster creation; for AKS/GKE, use managed secret encryption options; document as mandatory landing-zone control. **Effort: 1-2 days** for new clusters, migration planning for existing clusters. |
| **K8S-012** | **High** | Workload Identity | No IRSA-equivalent workload identity boundary is defined | No `eks.amazonaws.com/role-arn` annotations, projected service account token configuration, or cloud workload identity bindings found in manifests; service accounts include `superadmin` at `reference-target/scenarios/insecure-rbac/setup.yaml:1-5` and `big-monolith-sa` at `reference-target/scenarios/hunger-check/deployment.yaml:31-35` | High because pods and nodes are not separated by cloud identity boundaries. Not Critical because no real cloud IAM role is present in the lab manifests. | A pod that reaches node metadata or inherits node credentials could access cloud APIs beyond its Kubernetes namespace. This does not generalise safely to AKS/GKE without workload identity patterns. | Standardise on IRSA for EKS, Azure Workload Identity for AKS, and GKE Workload Identity; deny IMDS from pods where possible. **Effort: 3-5 days** platform pattern plus app onboarding. |
| **K8S-013** | **High** | Image Supply Chain | Workload images are unpinned or implicitly `latest` | Examples: `reference-target/scenarios/batch-check/job.yaml:12`, `reference-target/scenarios/build-code/deployment.yaml:17`, `cache-store/deployment.yaml:37`, `reference-target/scenarios/hunger-check/deployment.yaml:72`, `internal-proxy/deployment.yaml:19,30`, `system-monitor/deployment.yaml:34`; all use untagged `madhuakula/*` images | High because mutable tags break reproducibility and provenance. Not Critical because image compromise still needs a malicious image publish/pull event. | A redeploy can silently pull different code from Docker Hub, invalidating tested artefacts and making incident reconstruction difficult. | Pin images by digest, enforce trusted registry admission, sign images with Cosign, generate SBOMs with Syft. **Effort: 2-3 days** to establish policy, **hours** per workload. |
| **K8S-014** | **High** | Image Supply Chain | `:latest` is used in privileged/security-sensitive jobs and base images | `reference-target/scenarios/docker-bench-security/deployment.yaml:35` `busybox:latest`; `reference-target/scenarios/health-check/deployment.yaml:17` `busybox:latest`; `reference-target/scenarios/kube-bench-security/master-job.yaml:29`, `reference-target/scenarios/kube-bench-security/node-job.yaml:12` `aquasec/kube-bench:latest`; Dockerfiles: `reference-target/infrastructure/batch-check/Dockerfile:1`, `reference-target/infrastructure/build-code/Dockerfile:1`, `reference-target/infrastructure/health-check/Dockerfile:1`, `reference-target/infrastructure/hidden-in-layers/Dockerfile:1` | High because mutable scanner/init images run with elevated host access. Not Critical because exploit requires upstream image compromise or unexpected change. | A changed `latest` image in a privileged pod can become a direct node takeover path without a code review in this repo. | Replace tags with versioned digests; scan and sign every image before promotion. **Effort: 1-2 days**. |
| **K8S-015** | **High** | Network | No Kubernetes NetworkPolicy resources exist | Repository-wide search found no `kind: NetworkPolicy`; default programme CNI is AWS VPC CNI with no NetworkPolicy enforcement | High because east-west traffic is open in a citizen-facing EKS estate. Not Critical because NetworkPolicy absence alone does not create code execution. | A compromised pod can laterally scan and connect to services in other namespaces unless blocked elsewhere. | Adopt Cilium or Calico for EKS/AKS/GKE-compatible NetworkPolicy enforcement; start with default-deny ingress/egress in high-risk namespaces. **Effort: 1-2 weeks** platform rollout. |
| **K8S-016** | **High** | Network / Exposure | Internal service is exposed as fixed NodePort `30003` | `reference-target/scenarios/internal-proxy/deployment.yaml:54-65`; `Service/internal-proxy-info-app-service`, `type: NodePort`, `nodePort: 30003` | High because NodePort bypasses normal ingress governance and exposes every node IP on that port. Not Critical because network reachability still depends on node security groups/firewalls. | A service intended as internal can become reachable through node IPs, especially in older VPC-per-environment tiers with inconsistent security group hygiene. | Replace NodePort with ClusterIP plus approved ingress/private ALB as needed; block NodePort via admission except break-glass namespaces. **Effort: 1 day**. |
| **K8S-017** | **High** | Cluster/API Exposure | Access script binds kubectl port-forwards to all interfaces | `reference-target/access-kubernetes-goat.sh:54,73,92,111,130,149,168`; uses `kubectl port-forward --address 0.0.0.0` | High because local admin/debug endpoints become LAN/VPC reachable. Not Critical because it is an operator script, not a persistent Kubernetes Service. | Running the script on a shared bastion or EC2 host exposes Goat services to other network users, undermining localhost-only assumptions. | Bind to `127.0.0.1` by default; require explicit `--public` flag and security group review for remote demos. **Effort: 2-4 hours**. |
| **K8S-018** | **High** | Cluster/API Exposure | Setup supports disabling TLS verification for kubectl and Helm | `reference-target/setup-kubernetes-goat.sh:6-35`; `--insecure` sets `--insecure-skip-tls-verify` and `--kube-insecure-skip-tls-verify` | High because it trains deployment tooling to ignore API server identity. Not Critical because it requires an operator choosing `--insecure`. | In a real pipeline, this pattern could allow man-in-the-middle API server impersonation or conceal wrong-cluster deployment. | Remove insecure mode from production scripts; require CA pinning/kubeconfig validation; fail CI if insecure flags are used. **Effort: 4-8 hours**. |
| **K8S-019** | **High** | Logging / Detection | No audit policy, audit log destination, or runtime detection configuration is present | No `audit-policy.yaml`, kube-apiserver audit flags, Falco, Tetragon, GuardDuty EKS Runtime Monitoring, or equivalent manifests found under `reference-target/` | High because several findings involve RBAC and node escape where detection is essential. Not Critical because absence of detection does not itself grant access. | The programme may not see service-account abuse, privileged pod creation, or Secret scraping until after impact. This is material given the trigger incident. | Enable EKS control-plane audit logs to CloudWatch/SIEM; deploy Falco 0.38.x or cloud-native runtime detection; alert on ClusterRoleBinding, Secret list, hostPath, privileged pods. **Effort: 3-5 days** initial rollout. |
| **K8S-020** | **High** | Admission Control / Pod Security | No cluster-wide Pod Security Admission or equivalent policy baseline is defined | No `PodSecurityPolicy`, Pod Security Admission labels, Kyverno/Gatekeeper baseline policies found, except a narrow defensive Kyverno policy at `reference-target/scenarios/kyverno-namespace-exec-block/kyverno-block-pod-exec-by-namespace.yaml:1-36` | High because privileged/hostPath workloads would be admitted without a central guardrail. Not Critical because admission absence needs a bad workload submission to cause compromise. | Teams can accidentally deploy pods that violate Restricted baseline, repeating the exact unsafe patterns present in kubernetes-goat. | Enforce Pod Security Standards Restricted by namespace label where possible; use Kyverno/Gatekeeper exceptions for controlled diagnostics. **Effort: 3-5 days**. |
| **K8S-021** | **Medium** | Pod Security | Normal workloads lack explicit `runAsNonRoot`, capability drops, read-only root filesystem | Examples: `reference-target/scenarios/build-code/deployment.yaml:15-23`, `cache-store/deployment.yaml:35-39`, `hunger-check/deployment.yaml:70-81`, `internal-proxy/deployment.yaml:18-39`, `kubernetes-goat-home/deployment.yaml:15-23`, `poor-registry/deployment.yaml:15-23` | Medium because it increases impact of app compromise but is not a direct cluster escape without another flaw. Not Low because no admission controller enforces safer defaults. | Containers likely run as image default, often root, with writable filesystems and unnecessary Linux capabilities. | Set `runAsNonRoot: true`, non-zero `runAsUser`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, and `readOnlyRootFilesystem: true` where app-compatible. **Effort: 1-2 days** across core workloads. |
| **K8S-022** | **Medium** | Pod Security | No explicit seccomp or AppArmor profile across workload manifests | No `seccompProfile` or AppArmor annotations found across scenario Deployments/Jobs/DaemonSets including `reference-target/scenarios/system-monitor/deployment.yaml`, `health-check/deployment.yaml`, `docker-bench-security/deployment.yaml`, `internal-proxy/deployment.yaml` | Medium because kernel attack surface remains broad. ## Assumptions and Non-Findings

- kubernetes-goat intentionally contains synthetic/demo secrets. Findings K8S-009, K8S-010, and K8S-028 are recorded because the pattern is unsafe, not because the demo values are real credentials.
- No Terraform `.tf` files were present in `reference-target/`; the AWS lab setup uses CDK Python under `platforms/aws-setup/aws-kind-ec2-cdk/`.
- No production EKS control-plane configuration was available. Findings about audit logging, etcd encryption, NetworkPolicy enforcement, and workload identity are based on absence of those controls in the reviewed artefacts plus the programme context supplied in `README.md`.
- The narrow Kyverno policy in `reference-target/scenarios/kyverno-namespace-exec-block/kyverno-block-pod-exec-by-namespace.yaml:1-36` is a positive control for blocking pod exec in one namespace; it does not constitute a cluster-wide admission baseline.
